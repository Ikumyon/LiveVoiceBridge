# LiveVoiceBridge 再設計プラン

> 過去の設計・実装記録です。現在の仕様は [現行設計](../architecture.md) を参照してください。

作成日: 2026-10-23

## 目的と前提

既存のフォルダ分類を引き継がず、責務・依存方向・状態の所有者が一貫した構成に再構築する。
単なるファイル移動ではなく、処理の境界と契約を作り直す。

- Python / PySide6、Rust / PyO3、外部TTSという技術構成は継続する。
- 旧import、旧設定スキーマ、旧内部APIの互換性は維持しない。
- 互換レイヤ、自動移行、旧実装へのフォールバックは作らない。
- 既存の機能は新設計の要件として整理する。内部実装の都合による振る舞いは維持しない。
- 固定UIはQt Designerの `.ui` に定義する。
- 現在の作業ツリーには未コミットの変更が多数ある。実装開始時に差分を記録し、現在の機能と変更内容を基準にする。変更の巻き戻しは行わない。
- この文書は設計の基準とする。実装と検証の結果は [実装記録](rearchitecture-implementation.md) を参照する。

## 現状で解消する問題

| 現在の箇所 | 確認できた問題 | 新設計での扱い |
| --- | --- | --- |
| `application/runtime.py` | 画面、接続、合成エンジン、設定、辞書、終了処理が同居する | 機能別サービス、画面Presenter、起動時の組み立てに分解する |
| `presentation/settings_dialog.py` | 設定編集に加え、辞書操作、エンジン取得、話者取得、接続確認まで扱う | 画面は編集と表示に限定し、各操作は機能別サービスに依頼する |
| `infrastructure/streaming/youtube.py` | 通信処理が読み上げ文の組み立てと音声キュー投入まで行う | YouTubeイベントを取得・変換するだけにする |
| `workers/speech.py` | Qtスレッド、設定変換、合成、DSP、再生、辞書操作の契機が結び付く | Qt非依存の読み上げ処理と外部実装を分離する |
| `application/models.py` / `ports.py` | 型と契約が一か所に集まる一方、実処理では辞書形式と具象クラスへの依存が残る | 型・契約・ユースケースを機能単位で所有する |
| TTS factory / registry / runtime | 選択・生成・起動の入口が分かれている | 登録と組み立てはhost、起動方針はspeech、通信はintegrationsに限定する |
| 棒読みちゃんの `synthesize_wav()` | 外部で再生する処理を無音WAVで合成処理に見せている | 外部再生の専用契約を設ける |
| `paths.py` / bootstrap / gRPC補助 | 配置への依存、実行時のimportパス操作、生成処理が混在する | インストール可能なパッケージ、明示したデータ配置、ビルド時生成に統一する |

`core` の各機能内には、必要に応じて `models.py`、`ports.py`、`service.py`、処理名を表すモジュールを置く。
最初から全機能に同じ空ファイルや多段の層を作らない。`utils.py`、`helpers.py`、巨大な共通モデル集は設けない。
`__init__.py` に処理や大量の再公開を置かない。

## 依存の規則

```text
host ──────────> desktop ──────────> core
  └────────────> integrations ─────> core
```

- `core` はQt、HTTPクライアント、ファイル保存、Rust拡張の具象APIをimportしない。
- `core` は標準ライブラリによる並行実行を使用できる。外部I/Oは注入された契約を通す。
- `desktop` はcoreの操作・型・通知を使用する。integrationsやhostを参照しない。
- `integrations` はcoreの契約を実装する。画面やPresenterを参照しない。
- `host/composition.py` だけが画面と具象実装を組み合わせる。
- core内の依存は `session → chat / speech / dictionary / settings / telemetry` を基本とし、逆向きのsession参照は作らない。
- settingsは機能別の設定型を集約できるが、各機能はsettings全体を受け取らない。必要な設定だけを渡す。
- 機能間の操作は公開サービス経由にする。他機能のキュー、ロック、内部状態を書き換えない。
- これらのimport制約と循環参照をCIで機械的に検査する。

## 処理と状態の設計

### コメントから読み上げまで

```text
YouTube / テスト入力
  → CommentReceived
  → 対象判定・読み上げブロック適用・コマンド解析
  → SpeechPlan（発話・SE・辞書操作を表す型付きの計画）
  → 読み上げ実行
      ├─ 音声合成 → DSP → WAV再生
      └─ 外部再生への送信
  → 進捗・完了・失敗の通知
  → Qtイベント配送 → 画面更新
```

- YouTube取得とテスト送信は同じ処理入口を使う。
- 元コメントと読み上げ用テキストを分ける。表示内容を読み上げの加工で失わない。
- 解析結果や内部キューに `dict`、文字列、リストを混在させない。境界には型付きデータを使う。
- JSON、HTTP、protobuf、PyO3の値はintegrationsで検証・変換する。
- `SpeechPlan` 内でコマンドと発話の順序を明示する。辞書操作だけのコメントも処理できるようにする。
- SEは独立した実行項目として表現し、発話に重ねる指定と直列再生する指定を区別する。

### 状態と並行実行

- セッション状態はsessionサービス、エンジン状態はspeechサービス、設定の確定値はsettingsサービスが所有する。
- メイン画面は状態の複製を持たず、スナップショットを表示する。
- 接続・停止・設定適用は単一の制御キューで直列化する。通信・合成・再生は画面スレッドの外で実行する。
- 合成は1系列、ローカル音声再生は1系列とし、次の合成と現在の再生を並行させる。
- キューに上限を設ける。満杯時は新規の読み上げ要求を拒否し、コメント表示は継続する。拒否件数を通知する。
- セッションIDと設定revisionを要求・結果に付ける。停止後や設定変更後に到着した古い結果を採用しない。
- 停止は「新規受付停止 → 保留要求破棄 → 実行中処理の完了またはキャンセル確認 → 所有リソース解放」の順とする。
- 直ちに中断できない外部呼び出しにはタイムアウトを設ける。処理が終了したことを確認するまで、同じリソースを次のセッションへ渡さない。
- 終了時の待機は画面スレッドをブロックしない。強制的なスレッド終了を通常の停止手段にしない。
- 外部プロセスは自分が起動したものだけを終了する。既存サーバーへの接続と所有プロセスの起動を区別する。

### 設定と辞書の適用

- 設定画面には型付きの編集ドラフトを渡す。画面から本体やワーカーの属性を変更しない。
- 表示設定はプレビュー可能にし、キャンセル時は確定値へ戻す。合成・接続設定は適用操作で確定する。
- 設定適用は検証、保存、revision更新、必要な再構成を一つのユースケースとして扱う。
- 保存失敗時は確定値を変更しない。保存後の接続失敗は新しい設定に対するエラーとして扱い、旧設定へ自動復帰しない。
- 合成設定と辞書は各発話の合成開始時に不変スナップショットを取得する。途中の変更で同じ発話の条件を変えない。
- 教育・忘却は計画上の位置でdictionaryサービスに依頼する。完了後のスナップショットを後続発話に使用する。

## TTSの契約

全エンジンを同じ形に見せるための疑似音声を廃止し、二つの契約を使う。

| 契約 | 対象 | 成功時の意味 |
| --- | --- | --- |
| `AudioSynthesizer` | VOICEVOX、COEIROINK、Qwen3 | 検証済みの音声データを返した |
| `ExternalSpeechOutput` | 棒読みちゃん | 外部アプリへの送信を完了した |

- 棒読みちゃんの送信完了を、実際の再生完了として扱わない。外部キューの再生時間・完了を推定する無音WAVは作らない。
- エンジンの能力は `EngineCapabilities` に明記する。話速、音程、話者、DSP、完了検知などを画面と処理の両方で参照する。
- 未対応のコメント制御は対象の制御だけを不適用とし、通知する。本文の発話は継続する。設定ファイル内の不正な組み合わせは読み込み時に拒否する。
- 共通の発話指定とエンジン固有の設定を分ける。全エンジンの項目を持つ巨大な設定型は作らない。
- 話者IDはエンジン内で意味を持つ識別子とし、表示名や並び順と分離する。
- 型付きの成功値か分類済み例外を返す。`None`、空音声、printによる失敗通知は廃止する。
- 接続確認・話者取得・初期化も画面から直接実行せず、speechサービス経由にする。
- Qwen3のモデル依存は専用サービス内に限定する。デスクトップ環境へ推論依存を持ち込まない。

## UI・保存・ビルド

- Viewはウィジェットの入出力、Presenterはユーザー操作とcore通知の接続を担当する。
- 固定の画面、設定ページ、ツールバー、空状態の表示領域は `.ui` に定義する。
- Pythonで生成するウィジェットは、コメント行、辞書行、検出デバイスなど実行時に変動する構造に限定する。
- `.ui` はパッケージ内リソースとして一つの方式で読み込む。固定部品の不足をPythonから補わない。
- ポータブル配布を正式方式とする。設定・辞書・効果音は配置先内のdata、フォームとアイコンは同梱リソースへ配置する。音声はRust所有PCMとして扱い、一時音声ファイルは生成しない。カレントディレクトリに依存させない。
- 書き込みは一時ファイルと置換で行い、破損した設定は明示的なエラーにする。
- 設定が存在しない初回起動だけ新しい既定値を作る。旧形式がある場合はエラーで知らせ、自動変換しない。
- Pythonの依存宣言と開発コマンドは `pyproject.toml` に集約する。Qwen3サービスは別の依存環境を持つ。
- protobufコードは開発・ビルド時に生成する。アプリ起動時のソース生成と `sys.path` の書き換えを廃止する。
- 起動はインストールしたパッケージのエントリポイントと `python -m livevoicebridge` に統一する。仮想環境への自動再実行は廃止する。
- native拡張はRustの高速処理・OS接続を担当し、ワーカー管理や画面操作を持たない。PyO3の型情報も整備する。

## 実施順序

| 段階 | 実施内容 | 完了条件 |
| --- | --- | --- |
| 0. 要件固定 | 現作業ツリーの差分、機能一覧、状態遷移、コメントコマンド、停止仕様を記録する | 維持する機能と新しく変える振る舞いが一覧で区別される |
| 1. 契約設計 | 機能別の型、ports、通知、TTS能力、設定スキーマ、import規則を定義する | Qt・ネットワーク・Rustなしでcoreの契約と状態遷移を検証できる |
| 2. 実行経路 | テスト入力から計画・合成・DSP・再生・通知まで新構成で実装する | 順序、キュー上限、停止、再開、設定revisionを検証できる |
| 3. 外部接続 | YouTube、全TTS、辞書、設定、メトリクス、更新確認を新契約へ実装する | 各接続の成功・失敗・タイムアウトを契約テストで確認できる |
| 4. 画面再構成 | main・settingsの責務をPresenterへ分解し、固定UIを.uiへ集約する | 通常画面・設定・辞書・PiP・状況表示が新サービスだけで動く |
| 5. 切替と削除 | エントリポイント、依存、配布、CI、説明書を更新し、旧構成を削除する | 旧import・旧起動処理・旧設定変換・互換コードが残っていない |
| 6. 受入確認 | 配布物とソース実行で一連の操作を確認する | 全体の完了条件を満たす |

段階は開発作業の順序を表す。移行途中の旧方式を製品内の選択肢として公開しない。
最終切替までの新コード検証にはテスト用の組み立てを使い、旧新を接続する互換アダプターは作らない。
既存テストは仕様の根拠として使い、旧クラスへのmonkeypatchや旧パスへの依存は新しい境界へ書き換える。

## 完了条件

- coreとintegrationsがQtなしでimport・テストできる。
- 画面からネットワーク、ファイル保存、TTS生成、ワーカー内部操作を直接呼んでいない。
- YouTubeとテスト送信が同じ読み上げ計画・実行経路を使う。
- 合成・再生の順序、先行合成、キュー満杯、停止中の再開、遅れて返る初期化結果を検証している。
- エンジン変更・辞書変更・設定保存失敗・接続失敗でも状態の所有者が一つである。
- 棒読みちゃんに疑似WAVがなく、外部送信と実再生の状態を混同しない。
- コメントコマンド、教育・忘却、SE、全TTS、PiP、メトリクス、更新確認が受入要件を満たす。
- 固定UIが `.ui` にあり、Pythonからの固定レイアウト生成が残っていない。
- 旧構成と旧設定への互換処理がなく、リソースが配布物に含まれる。
- 新構成全体にlint・型検査・Pythonテスト・Rust検査・依存境界検査が適用され、広範囲の型検査除外がない。
- Windowsでは実機の外部エンジンと音声出力を確認する。Linuxでは現行CI相当の品質確認に加え、音声再生を環境上で確認する。macOS対応を掲げる場合は別途実機確認する。

## 採用しない設計

- 分散サービス化や汎用プラグイン基盤への全面変更。
- 全処理のasyncio化。Qt、同期HTTP、gRPC、音声再生の接続に必要な並行実行だけを設ける。
- 汎用イベントバス、サービスロケーター、巨大なAppContextによる暗黙の依存。
- ファイルを分割しただけで、旧アプリオブジェクトを各所から参照する構成。
- 合成キャッシュの再導入。現在の「同じ文も都度合成する」要件を維持する。

最初の実装単位は、機能別の型・契約とテスト入力による読み上げ実行経路とする。
この経路で状態・停止・設定適用の規則を確立してから、外部接続と画面を接続する。
